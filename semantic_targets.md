# Semantic Targets for Experiments

This document defines the parts of the current system that are actually
semantic, meaning they come from menu content and should be preserved by any
new extraction approach.

It intentionally ignores large amounts of `.menu` and `.rmf` filler/default
output that are currently generated by code.

## Why This Exists

The current pipeline is optimized around extracting directly into a fairly rigid
schema. For the experiments, we want to separate:

1. truthful menu understanding
2. code-level translation into target formats

That means we need to understand the real information contract behind the
current outputs.

## Current Pipeline Layers

The current end-to-end pipeline is:

1. ADE parse -> markdown
2. ADE extraction -> minimal payload
3. minimal payload -> intermediate representation (IR)
4. IR -> `.menu` JSON
5. IR -> `.rmf` XML

Important architectural fact:

- both `.menu` and `.rmf` are downstream renderings of an internal menu model
- RMF is generated from the intermediate payload, not from the final `.menu`

## The Real Semantic Core

From the mapping layer and RMF builders, the current system mostly cares about
the following menu facts:

### Restaurant/menu-level facts

- restaurant/store id if supplied externally
- global operating hours

### Category/group facts

- category name
- category description
- category sort/order
- category type or family classification
- category-level hours
- category-level sizes
- category-level option groups
- category-level toppings/modifier sets

### Item facts

- item name
- item description
- item sort/order within category
- base price when not size-priced
- explicit sizes and their prices
- item-level option groups
- item-level toppings
- item PLU if explicitly present

### Option-group facts

- option-group name
- option-group scope:
  - category-level
  - item-level
- min required
- max allowed
- choices/selects
- whether pricing varies by size

### Choice/select facts

- choice name
- choice flat price
- choice price by size

### Topping facts

- topping group name
- topping name
- topping price
- topping price by size if known
- whether topping is default

### Hours facts

- global hours
- category-specific hours
- day shutoff
- open/close time
- whether extracted hours are explicit vs defaulted

## What Is Actually Semantic in `.menu`

The final `.menu` schema is very large, but most of it is platform defaults,
flags, placeholders, and location-level settings.

The extractable subset is much smaller. In practice, the semantic content used
by the current code is:

- `Hours`
- `Categories`
- `Items`
- `Options`
- `Toppings`

Within those, the important fields are mostly:

### Categories

- `Id`
- `Name`
- `Description`
- `Sort`
- `CategoryItems`
- `CategoryOptions`
- `CategorySizes`
- category-level hours before they are lifted into top-level `Hours`

### Items

- `Id`
- `Name`
- `Description`
- `Price`
- `Sort`
- `SizeLabel`
- `ItemOptions`
- `ItemSizes`
- `ItemToppings`
- `PLU` if explicit
- `OnlineDescription` if explicit

### Options

- `Id`
- `Name`
- `MinRequired`
- `MaxAllowed`
- `OptionSelects`

### OptionSelects

- `Id`
- `Name`
- `Price`
- `OptionSelectPrices`

### ItemSizes / CategorySizes

- `Name`
- `Price`
- `SizeId`

### Toppings

- `Id`
- `Name`
- `Price`
- `PriceHalf`
- `ToppingGroup`
- `ToppingPrices`

The rest of the `.menu` object is largely generated/default-filled in
[expected.py](/home/softsensor/AntiGrav/Menu/menuocr/mapping/expected.py#L447)
and [base.py](/home/softsensor/AntiGrav/Menu/menuocr/mapping/base.py#L60).

## What Is Actually Semantic in RMF

The RMF layer consumes the intermediate representation, not the full `.menu`
object. The RMF builders mainly care about these IR fields:

- category `Name`, `Description`, `CategoryType`, `Sort`
- category `CategoryItems`
- category `CategoryOptions`
- category `CategorySizes`
- item `Name`, `Description`, `Price`, `ItemOptions`, `ItemSizes`,
  `ItemToppings`, `PLU`, `OnlineDescription`
- option `Name`, `MinRequired`, `MaxAllowed`, `OptionSelects`
- option select `Name`, `Price`, `OptionSelectPrices`
- topping `Name`, `DefaultTopping`, `ToppingGroup`, `ToppingPrices`

That means the semantic RMF source model is basically:

- groups/categories
- items
- sizes
- modifier categories
- modifiers
- preferences
- preference members
- group/item/item-size xrefs
- explicit descriptions
- explicit PLUs

Important RMF behavior:

- many RMF tables are real renderings of semantic menu data
- many other RMF tags are placeholders only
- canonical ordering matters even when a table has no real rows

## Implication for the New Experiments

A good experimental extraction target should preserve ambiguity and provenance,
not force early decisions that are really translation concerns.

Examples:

- "small / medium / large" should be captured as size facts before forcing
  Menufy `SizeId` rules
- "choose one side" should be captured as a choice prompt before deciding
  whether it becomes a preference vs modifier group in RMF
- unclear toppings vs add-ons should stay explicit in the extracted meaning
  instead of being over-normalized too early

## Recommended Direction

The best long-term target is not ADE's current rigid minimal schema and not the
full `.menu` schema either.

The better target is:

1. natural-language extraction of all menu facts
2. a custom semantic intermediate structure we define
3. code translators from that semantic structure into:
   - current minimal payload if needed
   - current IR
   - `.menu`
   - `.rmf`

For the immediate experiments, we should only tackle step 1 first.
